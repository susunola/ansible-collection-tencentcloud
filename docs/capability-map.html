▲ 领先项（实测数据）
  • 覆盖面第一梯队：模块总数 524、幂等 write 313，均高于三家官方云 Collection（含全腾讯云 2000+ API 的长尾只读覆盖）。
  • 生成式治理：199 个模块由 spec 生成、禁止手改，幂等 + check mode 全量内置；三类官方库大量模块为半手写维护。
  • 质量门槛：unit + contract 双测试、sanity 2.19/2.20/2.21 全绿、零 ignore 豁免，测试密度高于多数官方模块。
▼ 差距项（需追赶）
  • 生态与信任：Galaxy 下载 0 vs 11.8M–90.5M；需持续 release、inclusion 申请（#89 进行中）与社区口碑积累。
  • 集成测试深度：21 targets（62 yml）vs amazon 160（690）/ google 115（468）；13 个旗舰模块（cvm_instance / vpc / cdb_instance / redis_instance / tke_cluster / clb_load_balancer / cos_object / scf_function / ckafka_instance / cbs_disk / eip / nat_gateway / subnet）尚无集成 target。
  • 单元测试广度有虚点：有专属单测文件的模块仅 271/524（312 个模块测试文件），write 模块 222/313 无单测（coverage-batching 扫描，175 个共享同一 helper 骨架）—— 语句覆盖率 60.9% 由 info 深测与少数 write 深测拉高，广度分布不均。
  • ansible-core 门槛：≥2.19 起步（2.16–2.18 已 EOL；三家 ≥2.16/≥2.17 为历史声明，实际 CI 只测最新版）—— 主动对齐演进，换取旧控制节点用户覆盖的部分代价。
  • 维护资源：个人维护（贡献 / 加入路径见 CONTRIBUTING.md）vs 厂商 + Red Hat/社区全职团队；issue 响应与版本节奏是长期风险。
