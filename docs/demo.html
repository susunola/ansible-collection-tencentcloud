这一页不是幻灯片。下面每一个代码块都可以直接复制粘贴运行，输出是真实形状（资源 id 已打码）。 整条链路就是仓库里 docs/examples/06_full_chain.yml 这一个文件 —— 网络基础 → Web 栈 → 回读校验 → 逆序拆除，四个 stage 之间由 role 自己传递 id，不需要人工抄任何东西。

开始前

安装
ansible-galaxy collection install susunola.tencentcloud

# 控制器上还需要 SDK（COS 源额外需要 cos-python-sdk-v5）
pip install "tencentcloud-sdk-python>=3.1.174,<4.0.0"

需要 ansible-core 2.19+ 与 Python 3.11+（1.0.0 起的下限，见 porting guide）。

凭据
# 环境变量（优先级：模块参数 > 环境变量 > profile 文件）
export TENCENTCLOUD_SECRET_ID=AKIDxxxxxxxx
export TENCENTCLOUD_SECRET_KEY=xxxxxxxx
export TENCENTCLOUD_REGION=ap-guangzhou

也支持 TCCLI 风格的 ~/.tencentcloud/default.configure profile，以及 STS AssumeRole。

这条链路会真实计费

CVM、CDB、Redis、CLB 都是按小时计费的资源，建起来之后只有跑到第 4 步才会停止计费。 演练完请务必执行拆除 —— 这就是为什么 example 里 teardown 是 --tags teardown 而不是另一个文件： 它和创建共用同一份变量，不会拆漏。

四步走完

1

先看它打算做什么（--check）

1005 个模块全部支持 check mode 与 diff mode，这一步不碰云端任何东西。

ansible-playbook docs/examples/06_full_chain.yml --check --diff \
  -e image_id=img-xxxxxxxx -e web_password='ReplaceWith-AStrongPassword1'
# 输出节选
TASK [susunola.tencentcloud.tc_vpc_foundation : ensure the VPC exists]
changed: [localhost] => (item=demo-foundation)

TASK [susunola.tencentcloud.tc_web_stack : ensure the CVM instance exists]
changed: [localhost]

PLAY RECAP *****
localhost : ok=14   changed=9   unreachable=0   failed=0   skipped=2
2

真跑一遍

ansible-playbook docs/examples/06_full_chain.yml \
  -e image_id=img-xxxxxxxx -e web_password='ReplaceWith-AStrongPassword1'
PLAY [Stage 1 - network foundation] *****
TASK [tc_vpc_foundation : ensure the VPC exists]        changed
TASK [tc_vpc_foundation : ensure the subnets exist]     changed (2)
TASK [tc_vpc_foundation : ensure the security groups]  changed

PLAY [Stage 2 - web stack on the new foundation] *****
TASK [tc_web_stack : ensure the CVM instance exists]    changed
TASK [tc_web_stack : wait for the instance to run]      ok
TASK [tc_web_stack : ensure the CDB instance exists]    changed
TASK [tc_web_stack : ensure the Redis instance exists]  changed
TASK [tc_web_stack : ensure the CLB exists]             changed
TASK [tc_web_stack : register the CVM behind the CLB]   changed

PLAY RECAP *****
localhost : ok=31   changed=14   unreachable=0   failed=0

注意 wait for the instance to run：这是内建的 waiter，不是 until 循环。 模块自己知道资源什么时候算就绪，playbook 里不用写轮询。

3

再跑一次 —— 什么都不该变

幂等性是这套模块被生成时就带上的属性，不是事后补的。同一条命令重跑：

PLAY RECAP *****
localhost : ok=31   changed=0   unreachable=0   failed=0

changed=0 是这一段真正要展示的东西：第二次运行不产生任何写操作。

回读校验（stage 3 已经在 playbook 里）

TASK [Show what the chain produced]
ok: [localhost] => {
    "msg": [
        "vpc: vpc-1a2b3c4d",
        "instances running: 1"
    ]
}
4

逆序拆除

ansible-playbook docs/examples/06_full_chain.yml --tags teardown
PLAY [Teardown - remove the chain in reverse order] *****
TASK [tc_web_stack : ...]        changed   # CLB / CDB / Redis / CVM 先走
TASK [tc_vpc_foundation : ...]   changed   # 依赖清空后 VPC 才能删

PLAY RECAP *****
localhost : ok=18   changed=11   unreachable=0   failed=0

顺序不是靠人记的：role 的 teardown 是 state 机的另一条分支， tests/unit/roles/test_role_task_contracts.py 里的 reverse-teardown 断言族保证它永远是创建的逆序。

为什么这值得看

你看到的背后是什么
--check --diff 有真实输出456 个 write 模块全部实现 diff mode；check mode 下 waiter 按设计空转，不会真的等
changed=0写模块统一走 compare → apply → wait 状态机，幂等是结构属性而非逐个手写
自动等待资源就绪module_utils/waiters.py + polling.py，另有 tc_wait action 插件可单独调用
teardown 顺序正确68 个 role 的 task 图有 6 个断言族在 CI 里守着，teardown 逆序是其中之一
id 不用手抄role 之间用 tc_*_result 传递，跨 play 由 hostvars 承接
